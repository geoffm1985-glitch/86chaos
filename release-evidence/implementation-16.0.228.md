AI contract

api/_ai-policy.js is the shared authority. Customer OpenAI identifiers are explicitly limited to gpt-5-mini, gpt-5.5, and gpt-5.5-2026-04-23. Default invoice/menu extraction uses gpt-5-mini via Responses with strict structured JSON, low reasoning, standard service tier, store:false, and a server-selected output limit. Unknown models fail closed. Client model/provider/tier/reasoning overrides are rejected and safely diagnosed. The maximum approved customer OpenAI tier is standard GPT-5.5. Internal diagnostics require the existing authoritative System Administrator authorization on the diagnostics route; their separate allowlist remains gpt-5-mini. No high-tier runtime model was added. Master admins using customer routes have the same ceiling.

Existing recipe, voice, Help, and manual Gemini calls use the shared model authority and budgets. Python insights and ordering remain deterministic. Approved Gemini identifiers remain the existing flash allowlist. Gemini fallback for invoice/menu extraction is off by default; AI_SCANNER_GEMINI_FALLBACK=true enables outage/transport/file-processing fallback within the original budget. AI_OPENAI_SCANNER_UNAVAILABLE=true selects configured fallback before spending the one-call menu budget. Confidence, malformed output, and difficult documents never trigger escalation. Existing environment names remain valid; CUSTOMER_OPENAI_MODEL, INVOICE_OPENAI_MODEL, MENU_OPENAI_MODEL and the optional fallback flags are additional server settings, not client controls. No environment was changed.

Invoice: 20 MiB, 40 pages, 20 MP/6000 edge, at most two provider calls, 32768 primary output tokens, eight requests/minute. Menu: 20 MiB, ten pages, 20 MP/6000 edge, one provider call, 8192 output tokens, six requests/minute. Existing compact/repair, recipe/voice/manual, plan, page-accounting, idempotency and per-user/workspace rate limits remain. Restaurant decisions

Extraction produces evidence, followed by deterministic normalization, product/noise classification, package conversion and workspace/vendor matching before any research. Prior mappings are reused without an extra AI matching call. New product memory is under vendors/{vendorId}/productMappings/{hashedSkuOrDescription}, accessible through existing safe-write server authorization; no global customer memory exists. Approval alone learns a mapping. Managers can inspect, edit and revoke in Inventory Vendors. Revocation stays revoked on later invoice approval. Changed package/UOM/price basis, substantial price difference and substitutions require review; contradictory duplicate SKUs cannot silently overwrite memory. Use counters and last-used times update only with approved receipt processing.

The parser separates cases, each, bags, packs, count, weight and volume, preserves ordered/shipped/received quantities, supports partial cases, and requires actual evidence for catch weight. Unknown case contents do not create a count yield. Existing Stock Matcher and Needs Review show concise explanations, pack/conflict warnings, received-unit/cost confirmation and review notes. The atomic invoice approval transaction applies quantities and latest cost together, with deterministic identity, duplicate no-op, approved-row before/after evidence and an audit record. Supply products are excluded from food-cost links.

Needs Review research first uses exact workspace/vendor memory, then at most 20 prior workspace invoices for SKU evidence, then the existing Open Food Facts lookup. The normal matcher already checks workspace aliases and vendor catalog SKU fields before research. Public lookup is explicit, rate-limited, product-only, bounded to five results, and always review-only. Audit references are saved with the reviewed invoice row; no raw webpages are saved. Arbitrary backend web search and unconfigured vendor catalog crawling were not enabled because no trusted catalog/search integration exists in this source. Weak evidence stays in review.

Approved inventory prices feed dimensional ingredient costing, approved recipe ingredient/yield costing and menu portions. Weight is never silently treated as fluid volume. Missing selected inventory items are not replaced by fuzzy matches. Partially loaded batch dependencies cannot report a fully costed batch. Manager-approved batch ingredients and usable yield live on existing recipes/menuDependencies, with record-level change evidence. New menu links require explicit per-link approval; estimated portions retain their label. Legacy manually saved statusless dependencies remain supported. Menu history flags missing review dates/links and reviews older than 90 days, using the existing edit screen. Approved dependencies alone drive zero-stock/86 impact, including batch-to-menu propagation. AI Order Assistant remains advisory and does not place orders or change pars.

Firebase read and write review

Inventory invoice history and menu scan history now use fixed 20-document getDocs cursor pages, startAfter, explicit refresh after mutations and viewer/workspace lifecycle protection. No increasing-limit reread or history listener remains. Invoice order history retains its existing 120-document listener only while AI Order is open. The app shell owns the Menu Intelligence dependency listener (500 on Menu Intelligence, 120 on Today); its duplicate child subscription was removed. Menu edit reads are capped at 401 and refuse a partial edit when over 400. Existing invoice processedAt index is reused. Menu/memory pagination uses document IDs; no index is added.

Menu Intelligence inventory changes from 55 to at most 350 records in the existing owner listener because the Today-sized summary hid restaurant ingredients from costing/review. Recipes gain one demand-driven, at-most-350-record shell listener only on Menu Intelligence to resolve approved batch yields; Recipes screen retains ownership of its own listener. Overall listener count on Menu Intelligence falls by one (remove child dependency and scan history subscriptions, add recipe subscription); shared-registry deduplication already reduced some baseline physical duplication, so no unsupported physical-listener savings claim is made. The screen warns when a bound is reached, and missing cost sources remain review items. Today/Manager Brief and Voice retain bounded/lifecycle-protected existing reads; no new background listener was added. Recipe batch editor adds one inventory listener (350 maximum) only while open, plus explicit recipe/linked-dependency reads (80 maximum).

Invoice approval: transaction reads one invoice identity plus vendor and selected stock/mapping documents (at most 2+2N before deduplication, N<=150); writes U unique inventory documents, M unique active mapping documents, one invoice and one audit, plus a vendor if new. Duplicate receipt writes zero documents. This groups the prior independent product writes and audit calls without claiming Firestore batching eliminates per-document billing. Menu approval writes L links plus one summary and one audit (L<=400) atomically; duplicate writes zero. Batch approval writes N links, removed old links, one recipe and one audit (N<=80); no-op writes zero. Mapping management uses one vendor read, at most 51 mapping reads for a 50-record page, or at most 150 direct SKU lookups. Edit/revoke uses an audit plus mapping write; no-op writes zero.

Schedule publish/import already uses batched writes, import chunks at 450, legacy restore chunks at 400 with deterministic identity/restore evidence. Those paths were left intact. The legacy restore's broad read is part of compatibility handling for malformed dates, not a daily summary query. Bulk prep, CSV inventory imports, inventory adjustments and human AI-order draft saves retain per-record offline queue/replay and audit semantics; they were not collapsed into an unproven transaction that would remove offline recovery or record audit. Payroll, ownership, security, permissions, billing and backup audit paths are unchanged.
