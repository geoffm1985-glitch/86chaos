# 86 Chaos 16.0.236 — POS Bridge Foundation

The bridge is dormant, server-only, inbound-only, and staging-only. It has no downstream processor and no UI. Ordinary JSON backup and restore deliberately exclude all bridge security, replay, receipt, sequence, mapping, and quota roots. Native disaster recovery needs a separately reviewed bridge-specific runbook; 16.0.236 provides no bridge restore command and performs no automatic retention deletion.

## Environment variables

Required to enable the bridge (absence keeps it disabled and fail-closed):

- `POS_BRIDGE_ENABLED`
- `POS_BRIDGE_ENVIRONMENT`
- `POS_BRIDGE_TOKEN_ISSUER`
- `POS_BRIDGE_TOKEN_AUDIENCE`
- `POS_BRIDGE_ASSERTION_AUDIENCE`
- `POS_BRIDGE_SIGNING_KEY_ID`
- `POS_BRIDGE_SIGNING_PRIVATE_JWK`

Optional:

- `POS_BRIDGE_SECURITY_EPOCH` (positive integer; defaults to `1`; the current Firestore global epoch can only raise it)

Testing-only/simulator context:

- `POS_BRIDGE_SIMULATOR_BASE_URL`
- `FIRESTORE_EMULATOR_HOST`
- `GCLOUD_PROJECT` (must be a `demo-*` project for simulator execution)

The signing JWK must be a separately generated ES256/P-256 private key. It must not be a Firebase service-account key, Shift4 key, or provider credential. Never print or commit its value.

## Surgical security repair contract

Client assertions include the current integer `credentialVersion`. Token issuance binds that value and the canonical public-key fingerprint to the installation state reread inside the replay/quota transaction. Rotation, suspension, same-`kid` key replacement, or assertion expiry during verification causes issuance to fail before `jti` consumption.

Human bridge administration rechecks Firebase revocation, Auth-user disabled state, the active canonical `workspaceMembers` record, actual OWNER/ADMIN flags, App Check, MFA, recent authentication, and the canonical restaurant record. Legacy workspace fields never replace a missing or inactive canonical membership.

Event POST responses use per-event results. A fully successful batch returns 200. A batch stopped by a rejected, conflicting, or retryable item returns 207 with all committed receipts, the failed position, and explicit later `unattempted` results. `retryable` reports `commitState: "unknown"`; retrying the whole batch remains safe.

Reconciliation distinguishes `checkpointWorkPending` from real transport gaps and advances at most 256 sequence slots per transaction. Repeated reconciliation calls converge an idle, fully present multi-window stream. Exact retries remain zero-write. `validationFailureAttempts` is aggregate durable counter evidence only; no rejected payload or event-level rejected receipt is retained.

## Cost and retention

Memory-adapter instrumentation measures one uncontended fresh staged event as 9 logical document reads and 5 logical writes in one transaction, including the canonical restaurant lifecycle read. An exact delivery retry measures 9 reads and 0 writes; a changed-delivery conflict measures 9 reads and 1 bounded counter write. These are implementation operation counts, not Firebase billing measurements: real emulator/production contention can retry transactions, cross-window continuation can add reads, and access-token plus quota admission add shared reads/writes outside staging. At 100/1,000/10,000 entirely fresh events, the simple no-retry staging projection is therefore 900/9,000/90,000 reads and 500/5,000/50,000 writes, before auth/rate overhead.

Payload deletion is disabled; immutable delivery and entity-version tombstones are retained. `_pos-bridge-maintenance.js` exposes only a bounded, tenant-scoped, dry-run capacity-report helper for a future authenticated maintenance route; there is deliberately no maintenance CLI in this release.

## Deferred

No POS UI, payment processing, outbox, staff/menu sync, active-active writer, inventory depletion, financial posting, schedule/time-clock/payroll posting, customer mutation, hardware integration, automatic retention, or bridge restore tooling is present.
