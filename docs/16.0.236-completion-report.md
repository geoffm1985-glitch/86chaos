## 6–14. Authentication and lifecycle

6. Machine authentication is independent of Firebase-human auth. Human ID tokens are accepted only by control-plane routes; POS assertions and bridge access tokens use dedicated JOSE paths and explicit token types.
7. Installations use server-issued opaque `pbi_` identifiers and states `pending`, `active`, `suspended`, and `revoked`. Activation makes tenant/location/namespace identity immutable, claims the single active writer for that scope, and revocation is terminal. Rotation increments credential version.
8. Registration, activation, rotation, suspension, revocation, and mapping changes require authenticated OWNER/ADMIN authority, App Check/MFA through the existing authorization path, and recent authentication for sensitive lifecycle actions. Permission-only team/settings roles are not admitted.
9. Client keys are ES256/P-256 public JWKs only. Private JWK fields, remote JWKS/certificate URLs, unsupported algorithms/key types, and malformed keys are rejected.
10. Client assertions use ES256, exact token-endpoint audience, identical `iss`/`sub` installation ID, required unique `jti`, explicit environment and assertion token type, maximum 60-second lifetime, and at most 30 seconds clock tolerance.
11. Access tokens are signed `at+jwt` bridge tokens with a five-minute maximum lifetime and no refresh token. They bind installation, restaurant, location, namespace, environment, credential version, security epoch, capabilities, issuer, audience, and token type.
12. The server signing key is an independent pinned ES256 private JWK configured only by environment. Missing/malformed production configuration keeps the bridge disabled and fail-closed.
13. Assertion `jti` consumption is recorded transactionally under a hashed replay identity. A consumed assertion cannot mint another token, including after process restart.
14. Every machine operation re-reads current installation, active location/scope, credential version, global/installation security epoch, and environment. Suspension/revocation/rotation therefore invalidate outstanding tokens. Security changes and their audit evidence commit atomically.

## 15–20. Tenant, capability, schema, PCI, and bounds

15. Firebase project selection comes only from deployment/server configuration. Claims, body, query, and headers cannot select a project. All tenant/location/namespace paths are derived from current server-side installation state; forged foreign identifiers fail without resource disclosure.
16. Capabilities report bridge `1.0`, app `16.0.236`, supported contract versions, `minimumPosVersion: null`, limits, time, and environment. Effective scope is the intersection of server support, installation approval, and token scope. Only event staging, receipt lookup, and reconciliation are supported; no outbox or synchronization capability is advertised.
17. The strict AJV envelope accepts only `eventId`, `eventType`, `schemaVersion`, `posInstallationId`, `sourceEntityType`, `sourceEntityId`, `sourceEntityVersion`, `sequence`, `occurredAt`, and `payload`. Unknown/server-authority fields are rejected with `additionalProperties: false`.
18. Canonical bounded schemas cover order snapshots/items/discounts/taxes/tips/tender summaries and cash sessions, with employee/menu references. Supported events are order opened/updated/closed/voided/refunded and cash session opened/closed. Money is integer cents and order lifecycle must match its snapshot.
19. Payment data is recursively allowlisted to operational totals, tender classification, and payment status. PAN/card number/CVV/track/PIN data, processor credentials, raw tokens, customer payment identifiers, unexpected payment objects, and all unknown fields are rejected. Raw requests, Authorization headers, tokens, assertions, and sensitive rejected values are not logged or echoed.
20. Limits: 20 events/batch; 256 KiB request; 32 KiB/event; 100 order items; depth 8; identifiers up to 128 ASCII characters; batch sequence span 256; ahead-of-contiguous window 4096; default page 50/max 200; manifest maximum 200. Compressed requests are rejected.

## 21–27. Staging, idempotency, sequence, reconciliation, mappings, and rate limits

21. Accepted events are authenticated, validated, authority-checked, idempotency-checked, and committed transactionally before acknowledgement. The only processing state is `staged`; there is no processor.
22. Delivery identity and logical entity/version identity use separate versioned canonical tuple hashes. Same ID/same content returns the original receipt with no write; changed delivery, sequence collision, or changed entity/version content conflicts; same logical content is a logical duplicate; unseen lower history is appended without replacing the current head.
23. Sequence evidence uses fixed 256-slot window documents plus separate highest-observed and highest-contiguous counters. Gap closure is bounded and honestly exposes `checkpointComplete` when additional work remains.
24. Entity-version documents are immutable logical tombstones; entity heads advance only for higher versions. Timestamp order never substitutes for source version order.
25. Reconciliation reports last receipt time, observed/contiguous sequence, unique/staged counts, duplicate/conflict evidence, missing count, checkpoint status, `processingEnabled: false`, `lastSequenceProcessed: null`, and bounded manifest states `present`, `missing`, `rejected`, or `conflicting`. It never claims semantic processing or complete order reconciliation.
26. Mappings are tenant/location/namespace-bound reviewed identifiers, not permissions. Only employee-reference creation is supported in this release; immutable external IDs, target authority, revision, status, approval evidence, and atomic audit are enforced. Other mapping creation is rejected.
27. Transactional fixed-size quota windows apply per proved installation and request class: 12 token exchanges/minute, 120 event requests/minute, 1,000 event submissions/minute, and 60 read/handshake requests/minute. Failures return 429 with `Retry-After`. Invalid signatures do not allocate attacker-selected installation quota documents.

## 28–34. Storage, cost, audit, restore, retention, and operational boundary

28. Firestore roots are `posBridgeInstallations`, `posBridgeScopes` (locations, streams, 256-slot sequence windows, events, entity versions/heads, mappings, control requests, and fixed quota windows), `posBridgeAuthReplays`, and `posBridgeControl`. Machine-derived document IDs are validated opaque IDs or versioned hashes; clients never supply Firestore paths.
29. Memory-adapter instrumentation measures an uncontended fresh stage at 8 logical document reads, 5 logical writes, and one transaction; exact retry at 8 reads, 0 writes, one transaction; changed-delivery conflict at 8 reads, 1 write, one transaction. Fresh-event projections are 800/500 reads/writes at 100 events, 8,000/5,000 at 1,000, and 80,000/50,000 at 10,000. These are implementation counts, not Firebase billing measurements; auth/rate admission and transaction retries add cost.
30. Registration, activation, rotation, suspension, revocation, and mapping mutations write sanitized `auditLogs` evidence in the same transaction. Event receipt evidence replaces per-event audit amplification. Secrets, JWTs, and raw payloads are excluded.
31. All bridge roots are explicitly excluded from ordinary JSON export. Backup metadata and preview expose the exclusion; selective restore rejects them; ordinary full restore skips legacy bridge entries. No bridge restore tool is introduced.
32. No automatic deletion is enabled. Identity/idempotency/entity tombstones persist. Maintenance exposes only a bounded, tenant-scoped, dry-run capacity report helper; bridge disaster recovery and resolved-payload retention require future reviewed procedures.
33. The centralized reserved-root guard blocks create/replace/update/delete through `api/safe-write.js` for every human role, including internal/super-admin paths. Behavior tests cover every reserved root and action.
34. Event staging writes only bridge roots. Behavioral tests compare all writes and prove no mutation of inventory, Daily Close, ledger/Financials, schedule, Time Clock, payroll, recipes, menu, vendor orders, par levels, or customer records.

## 45–48. Limitations, risks, and status

45. Deferred by design: POS application/UI, payment processing, hardware, outbox, staff/menu synchronization, active-active failover, operational posting, automatic retention, bridge restore tooling, and a production POS-version compatibility policy.
46. Remaining security risk: emulator rules/concurrency behavior and deployed-host negative behavior still require execution in the certified Java 21+/Firebase/deployment environment. Secret provisioning, key rotation operations, and platform logging/redaction must be reviewed during deployment. The bridge is fail-closed while required configuration is absent.
47. Remaining data-integrity risk: real Firestore retry/contention and long-gap behavior are implemented and covered by the required emulator suite but were not executable on this Java 17 runner. Native disaster recovery semantics and any future payload cleanup remain intentionally undefined rather than unsafe.
48. Status: **implementation complete; local non-emulator targeted validation passed; required emulator/rules validation blocked by the runner; not fully certified**. Full certification requires Java 21+ emulator/rules success and the complete release gate.
