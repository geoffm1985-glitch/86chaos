# 16.0.232 deferred schedule risks

## Emergency schedule restore delivery ordering

Verified in `api/schedule-restore-utils.js` and its callers, including `api/import-cheers-july-schedule.js`:

1. The server builds an in-memory backup object.
2. Existing schedule records are deleted in committed batches.
3. Replacement records are written in committed batches.
4. The response containing the immediate recovery backup is returned only after those mutations finish.

If the request or browser is interrupted after deletion/replacement begins but before the response is delivered, the administrator may not receive that immediate recovery artifact. This release does not redesign restore semantics because doing so would materially broaden a schedule-integrity release into a destructive recovery-flow rewrite.

Recommended next release: persist and verify a recoverable server-side backup before the first destructive commit, bind it to the authorized workspace/restore operation, and add interruption/retry/idempotency coverage before changing the live restore flow.

## Intentionally unchanged compatibility behavior

16.0.232 does not retire schedule rescue queries, narrow My Schedule history, migrate historical records, delete duplicate candidates, change publication recovery, or alter restore/import interpretation. The Schedule Integrity Audit is evidence-only and never authorizes mutation.
